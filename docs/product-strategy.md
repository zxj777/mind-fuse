# Mind-Fuse 产品策略

## 文档定位

这份文档是当前项目内的**正式产品策略文档**。

- 它承接多轮产品讨论后确认的 **v2 产品定义**
- 它用于指导后续 MVP 设计、信息架构和实现取舍
- 根目录 `plan.md` 代表旧的 Diagram/技术图表方向
- 根目录 `new-plan.md` 和 session 讨论稿保留为过程材料，不再作为当前正式产品定义

一句话说：**以后谈当前产品方向，以这份文档为准。**

## 为什么要切换方向

项目原有叙事围绕“AI 驱动的技术图表/Diagram 生成白板”，但新的产品判断已经变化：

- 用户真正需要的不是“更快画图”
- 也不是“让 AI 直接解释一切”
- 而是帮助开发者在复杂信息环境下形成、验证、回访自己的技术理解

已有白板底座仍然有价值，但应被视为**可复用基础设施**，而不是产品身份本身。

## 一句话定位

> **一个让开发者在完成手上事情的同时，顺便沉淀出可被未来自己复用的技术判断的工作台。**

关键点在于：**“顺便”**。

用户不是为了“管理知识”或“形成判断”而来；判断是用户在完成真实任务过程中自然沉淀出来的产物。

## 用户当下真正要完成的事

产品入口必须贴近真实任务，而不是抽象的“知识管理”。

| 场景 | 用户当下想完成的事 |
| --- | --- |
| 搞懂一个具体问题 | “这个东西到底怎么工作的” |
| 学一个新领域/新技术 | “我想系统理解 X” |
| 做一个技术决策 | “选 A 还是 B” |
| 写一个解释/文档/分享 | “我得讲清楚这件事” |
| 评审一个设计/PR | “这个方案合不合理” |

这意味着产品首页、主题入口、capture 入口、snapshot，都要围绕“当前任务”组织，而不是围绕“笔记空间”组织。

## 产品核心

### 核心 1：低打断 capture

低打断 capture 不是附属能力，而是产品核心之一，也是最可能形成隐形护城河的地方。

理想状态下，用户在 IDE、浏览器、文档、AI 对话里出现“这个值得记下来”的瞬间时：

- 投递动作不超过 1 步
- 不需要离开当前上下文
- 不被强制命名、分类、关联
- 可以稍后整理，但不会丢失

如果这一点做不到极致，产品会迅速退化成“高级但沉重的技术笔记工具”。

### 核心 2：跨来源收束到当前问题

产品不是帮用户收集信息，而是帮用户把分散来源收束到**当前正在追的问题**上。

来源可以包括：

- 源码
- 文档 / RFC
- AI 对话
- Issue / PR / 讨论串
- 文章 / 二手材料
- 用户自己的瞬时想法

这里的关键不是“先定义结论”，而是先围绕 **Question** 归集材料。

原因很简单：

- 问题通常是真实存在的
- 结论往往是后续才浮现出来的
- 如果过早要求用户给出结论，容易产生假的结构化沉淀

所以，产品的组织中心应该优先是 **Question**，而不是 **Conclusion**。

## 差异化能力

### 让沉淀的内容在合适时机重新出现

大多数知识工具的问题，不是“不能保存”，而是“保存后再也不会回来”。

Mind-Fuse 要解决的不是“能不能回访”，而是：

> **有没有足够自然的回访理由。**

优先级从弱到强的触发方式可以是：

| 触发器 | 强度 | 例子 |
| --- | --- | --- |
| 用户打开相关 topic | 弱起点 | “你之前在这个主题下有 2 个未闭合问题” |
| 当前任务和旧 topic 强相关 | 中 | “你现在正在看的内容，和旧主题 X 有关联” |
| 新材料与旧 question 高相关 | 强 | “你 3 周前问过的 Y，这条新材料可能相关” |
| 用户主动搜索 | 兜底 | 通过关键词 / 内容搜索历史判断 |

MVP 阶段必须从**最弱、最不打扰**的触发方式开始，禁止直接做高频主动 push 通知。

## 长期价值：个人技术理解资产

随着使用积累，用户留下来的不只是零散笔记，而是：

- 问过哪些问题
- 哪些问题已经闭合，以及为什么闭合
- 哪些问题仍未闭合
- 对同一问题的判断如何随时间变化

这些东西会逐步形成用户自己的**技术理解资产**。

这是一种长期护城河，但它不应该作为 MVP 阶段的主要卖点。MVP 先要证明的是：产品真的比“AI + 笔记 + 临时草图”更顺手、更容易回到上下文。

## 对 v1 产品叙事的修正

此前讨论里存在一些已经被修正的表述，当前统一以 v2 为准：

| 维度 | v1 | v2 |
| --- | --- | --- |
| 用户来意 | 形成技术判断 | 完成手上的事，顺便沉淀 |
| Capture 地位 | 使能层 | 核心能力 |
| 组织中心 | 结论 | 问题 |
| 验证机制 | 用户持续显式操作 | 更多作为内部能力，在整理时出现 |
| 回访目标 | 恢复上下文 | 制造回访理由 |
| 长期资产 | 北极星卖点 | 隐形长期价值 |

## 对当前代码库的直接影响

### 可以继续复用的部分

- `packages/types` 中的基础类型、ID、Shape/Binding/Group 体系
- `packages/collaboration-core` 中的 `DocumentManager` 与空间索引能力
- 现有画布底座作为“知识节点卡片 + 关系线”的承载层

### 不应继续沿旧方向深化的部分

- 旧 Diagram/图表生成叙事
- 以“AI 自动生成图”为核心卖点的路线
- 先做复杂白板通用能力，再补产品闭环的路径

## MVP 约束

第一版要验证的是一个窄闭环，而不是完整知识系统：

1. 用户能否低打断地收集碎片
2. 用户能否把碎片逐步收束到问题
3. 用户几天后能否恢复主流程、未解问题、已确认结论和下一步

明确不优先：

- 完整协作
- 完整 IDE 能力
- 通用知识库
- 高自动化 AI 生成图
- 复杂主动通知系统

## 当前最关键的两个风险

1. **问题为中心是否真的成立**

用户自然记录的往往是片段、观察和引用，不一定会主动写成问题。后续可能需要设计“片段 -> question”的辅助转换能力。

2. **回访触发器是否会变成打扰**

如果提示时机和相关性判断不准，回访系统会迅速变成噪音。MVP 必须保守，从被动提示做起。

## 当前阶段的工作原则

1. 先验证产品闭环，再扩大能力边界
2. 先定义信息架构和领域模型，再谈复杂画布能力
3. 白板是承载层，不是产品定义本身
4. AI 是帮助理解和回访的辅助层，不是产品中心

## 当前结论

Mind-Fuse 不再应该被定义为“AI 驱动的技术图表白板”。

它当前更准确的定义是：

> **一个帮助开发者在真实工作与学习任务中，低打断地收集信息、围绕问题收束材料、并在未来重新找回技术判断上下文的工作台。**
